# TheoryMCP namespace-assisted lab deployment for lesser-host

`lesser-host` deployment and stewardship workflows may use the hosted TheoryMCP service for deploy guidance, agent
memory, and knowledge tools. TheoryMCP authentication is separate from the AWS credentials used by the AppTheory
deploy contract. An MCP authentication prompt does not mean `lesser-host` needs to deploy or bypass
`theory-mcp-server`.

This runbook prepares a lab deployment against a **pre-vended TheoryMCP namespace** while preserving both security
boundaries:

- TheoryMCP keeps route-scoped authentication and server-owned namespace authorization.
- lesser-host keeps its AppTheory deployment contract and Factory-submodule provenance guard.

## Scope

- Applies to `lesser-host` lab planning and deployment preparation.
- Does not deploy, vendor, fork, or reconfigure the proprietary `theory-mcp-server` service.
- Does not disable OAuth or create namespace credentials.
- Lab only. An operator-issued harness key may be used for an already-vended lab namespace; it is not a namespace
  bootstrap mechanism and remains unavailable on live.

## Prerequisites

- A TheoryMCP namespace and optional agent route vended by TheoryCloud.ai.
- Route-scoped Autheory OAuth access, or a lab harness key issued by the TheoryMCP operator.
- The `theory` CLI.
- A local clone of `factory` with the `products/lesser-host` submodule initialized for eventual deployment.
- Valid AWS credentials are not needed for the offline planning step.

## Step 1 — Obtain the routed namespace from the owner

TheoryMCP's account-owned namespace vending API is an internal `AWS_IAM` contract between TheoryMCP and
TheoryCloud.ai. Its caller role is created in the TheoryMCP account and trusted to the TheoryCloud.ai account. A
lesser-host operator does not call that API directly or replace it with a client-generated key.

Request these non-secret values from the owner:

- `client_namespace` (for example, a namespace dedicated to the job-finder project);
- optional `agent_id`;
- stage (`lab` for this runbook);
- the approved authentication path: route-scoped OAuth, or an operator-issued lab harness key.

## Step 2 — Render the offline plan

From this repository, run:

```bash
bash scripts/plan-theorymcp-assisted-deploy.sh \
  --client-namespace <your-namespace> \
  --agent-id <your-agent-id> \
  --profile default
```

The planner:

- validates the namespace and agent route segments;
- prints the routed MCP URLs and authentication posture;
- invokes `theory app up` without `--execute`, producing only the symbolic AppTheory preview;
- never calls AWS and refuses `live`, `--execute`, and `--confirm-live`.

If the TheoryMCP operator specifically issued a lab harness key, add `--auth-mode harness`. Do not put the key on
the command line or in git; configure it in the MCP client's secret store.

## Step 3 — Prepare the Factory deployment checkout

Actual lesser-host deployment is provenance-gated. A standalone clone is intentionally rejected. Initialize the
registered submodule:

```bash
git -C ../factory submodule update --init products/lesser-host
```

The eventual `theory app up --execute` command must run from `factory/products/lesser-host` at an approved commit.
Do not update or commit the Factory gitlink merely to prepare the local checkout.

## Step 4 — Authenticate without bypassing authorization

Preferred: let the MCP client follow the route's RFC 9728 challenge and complete Autheory OAuth for the exact routed
resource.

Lab exception: use a harness key only when the TheoryMCP operator provides one for the already-vended namespace.
The key is namespace-scoped, expiry/status/scope checked, and unavailable on live. It is not generated by lesser-host.

## Step 5 — Deploy after AWS credentials are available

After the offline plan is approved and the `default` profile contains valid credentials, run from the Factory
submodule:

```bash
AWS_PROFILE=default AWS_REGION=us-east-1 theory app up --stage lab --execute
```

The command uses `app-theory/app.json` and `scripts/app-theory-cdk.sh`. Do not invoke CDK directly and do not set a
timeout on the deployment.

## Hard boundaries

- Never bypass or disable TheoryMCP authentication in lesser-host.
- Never commit OAuth tokens, harness keys, AWS credentials, or namespace-vending receipts.
- Harness keys are lab-only and must be issued by the TheoryMCP operator for an already-vended namespace.
- theory-mcp-server is consumed as a hosted service; do not vendor or redistribute it from the equaltoai corpus.
- A symbolic preview is readiness evidence, not deployment evidence.
